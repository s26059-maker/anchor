# Anchor

FPS 핵을 "잡는" 게 아니라 **핵이 얻을 이득을 구조적으로 0으로 만드는** 서버 권위형 안티치트.
정직한 플레이어와 핵 유저는 뇌가 같다. 다른 건 정보와 손뿐이다. Anchor는 그 둘을 서버와 하드웨어에 묶는다.

## 실행

```bash
go run ./cmd/experiment -rounds 4000 -latency 20
```

Go 1.22 이상. 외부 의존성 없음(표준 라이브러리만).

## 구조

```
internal/
  geom/    벡터, 선분 교차
  world/   서버만 가진 진짜 게임 상태 (벽, 플레이어, 시야선)
  gate/    가시성 게이트 = 정보의 닻. 보낼 적만 고른다
  netsim/  서버 → 클라이언트 지연
  bot/     사람 반응 모델. 월핵 = 같은 뇌 + 벽 뒤 데이터 사용
  duel/    코너 피크 1대1 라운드
  decoy/   미끼 섞기: 진짜 적 ID를 라운드마다 새 핸들로, 진짜+미끼 순서까지 섞기
  evidence/ 계정별 대안 혼합 e-value
cmd/experiment/   실험 1: 가시성 게이트
cmd/experiment2/  실험 2: 선공개 구간 미끼 + 판정
```

## 실험 1: 가시성 게이트가 월핵을 얼마나 지우나

홀더가 벽을 지키고 피커가 위·아래 중 한쪽으로 무작위 시점에 튀어나온다. 편도 지연 20ms.
아래는 같은 로직의 Python 포팅으로 미리 돌린 값(라운드 1,500개씩)이다. Go 실행 결과로 교체할 것.

| 게이트 | 선공개(ms) | 정직한 홀더 승률 | 월핵 홀더 승률 | 월핵 이득 | 공정성 왜곡 | 숨은 적 누출률 |
| --- | --- | --- | --- | --- | --- | --- |
| 끔 | - | 31.0% | 100.0% | +69.0%p | 0 | 100% |
| 켬 | 0 | 48.3% | 48.3% | 0 | +17.3%p | 0% |
| 켬 | 20 | 31.0% | 52.3% | +21.3%p | 0 | 0.87% |
| 켬 | 50 | 31.0% | 76.7% | +45.7%p | 0 | 2.0% |
| 켬 | 100 | 31.0% | 96.2% | +65.2%p | 0 | 3.8% |
| 켬 | 200 | 31.0% | 100.0% | +69.0%p | 0 | 7.5% |

### 알아낸 것

- 게이트를 끄면 월핵은 **100%** 이긴다. 벽 뒤 정보가 전부 메모리에 있기 때문이다.
- 선공개를 0으로 하면 월핵 이득이 **정확히 0**이 된다. 대신 지연 때문에 적이 늦게 튀어나와(pop-in) 정직한 피커가 17%p 손해를 본다. 공정성을 깨는 차단은 차단이 아니다.
- 선공개를 지연(20ms)만큼만 두면 공정성은 돌아오지만 월핵이 **+21%p**를 가져간다. 누출률 0.87%, 틱으로는 한 줌이 승부를 가른다.
- 선공개가 100ms면 누출률 3.8%로 거의 막은 것처럼 보이지만 월핵 승률은 96%다. **누출률은 거짓 안심을 준다.** 봐야 할 건 승률이다.

### 왜 게이트만으로는 0이 안 되나

선공개 구간이 있어야 정직한 사람 화면이 공정하다. 그런데 그 구간의 데이터는 월핵도 읽는다.
이 구간은 없앨 수 없으니, 그 안의 정보를 **믿을 수 없게** 만들어야 한다. → 실험 2(미끼).

## 실험 2: 선공개 구간 미끼

```bash
go run ./cmd/experiment2
```

실험 1에서 남은 월핵 이득(+18%p)을 미끼로 지운다. 미끼는 두 종류다.

- **거울 미끼**: 진짜 적이 선공개되는 순간, 반대편 출구에도 똑같이 움직이는 가짜를 보낸다. 월핵은 어느 쪽이 진짜인지 모른다.
- **무작위 미끼**: 아무 때나 출구 직전까지 왔다가 사라진다. 여기에 반응하면 증거가 쌓인다.

미끼는 절대 화면에 보이는 위치까지 오지 않는다. 정직한 사람 화면엔 아무 일도 안 일어난다.

### 만들다가 찾은 구멍

처음엔 미끼를 넣어도 월핵 승률이 거의 안 떨어졌다. 원인은 **ID**였다.
진짜 적은 게임 내내 같은 ID로 오니까, 치트는 "처음 보는 ID = 미끼"로 바로 걸러낼 수 있었다. 목록 순서도 마찬가지다(진짜가 항상 먼저).
그래서 진짜 적 ID를 라운드마다 무작위 핸들로 바꾸고 순서까지 섞는다(`decoy.Mixer`). 실제 게임에 넣을 때도 반드시 지켜야 하는 규칙이다.

### 예상 결과 (Python 포팅)

| 홀더 전략 | 미끼 켬 승률 | 정직 대비 이득 | 미끼 반응률 | 밴까지 라운드 |
| --- | --- | --- | --- | --- |
| 정직 | 32.5% | 0 | 10% | 밴 안 됨 |
| 월핵, 신호 100% 믿음 | 24.2% | −8%p | 84% | 약 30 |
| 월핵, 50%만 믿음 | 27.1% | −5%p | 47% | 약 160 |
| 월핵, 20%만 믿음 | 28.5% | −4%p | 26% | 안 잡힘 |
| 월핵, 5%만 믿음 | 30.4% | −2%p | 13% | 안 잡힘 |

월핵을 쓰면 **어떤 전략이든 정직하게 하는 것보다 손해**다. 믿으면 잡히고, 안 믿으면 이득이 없다.
조금만 믿는 월핵은 잡히지 않지만, 이득도 음수다. 이게 Anchor가 말하는 "이득 0"이다.

이 결론은 벽 뒤 신호를 어느 정도 **믿는(방향을 그대로 따라가는)** 월핵에만 해당한다. 신호를 안 믿고
개수만 세는 치트가 있다면? → [2.5단계](#25단계-smartwallhack-레드팀과-그-방어).

## 2.5단계: SmartWallhack 레드팀과 그 방어

### 알아낸 구멍

실험 2의 미끼는 진짜 적이 선공개될 때 항상 거울 미끼와 **쌍**으로 오고, 무작위 미끼는 **혼자** 온다.
치트가 벽 뒤 신호를 전혀 믿지 않고 그냥 **개수만** 세면, 방향 정보 없이도 미끼를 걸러낼 수 있다.

### 레드팀: SmartWallhack

`internal/bot`의 `Human.Smart` 모드. 벽 뒤 신호가 혼자 오면(개수=1) 미끼로 보고 **완전히 무시**한다
(에임을 절대 안 움직인다 → 미끼 증거 0). 쌍으로 오면(개수≥2) 어느 쪽이 진짜인지는 여전히 모르지만
**반응 타이머만 그 순간부터 미리 돌린다**. 실제로 적이 화면에 나타나 방향이 확인되면 그때 에임을
돌리는데, 타이머가 이미 돌고 있었으니 반응 지연이 거의 0이다. 방향 정보는 하나도 못 얻지만 타이밍
정보만으로 이긴다.

```bash
go run ./cmd/experiment2
```

측정 결과(게이트 켬, 선공개 20ms, 지연 20ms, 라운드 20,000개, 쌍 빈도 0% = 기존 상태, A·B 표):

| 홀더 전략 | 미끼 켬 승률 | 이득(정직 대비) | 미끼 반응률 | B 표 밴 |
| --- | --- | --- | --- | --- |
| 정직 | 31.8% ± 0.6%p | 0 | 10.6% | 0% |
| 월핵, 신호 100% 믿음 | 24.0% ± 0.6%p | −7.9%p ± 0.9%p | 83.3% | 100%(중앙값 32라운드) |
| **SmartWallhack** | **37.3% ± 0.7%p** | **+5.5%p ± 0.9%p** | **10.8%(정직과 구별 안 됨)** | **0%(최대 log₁₀E = −1.7)** |

예상대로다. 신호를 100% 믿는 기존 월핵은 미끼에도 83% 반응해서 평균 32라운드 만에 밴된다(오히려
정직보다 −7.9%p 손해). SmartWallhack은 미끼에 단 한 번도 반응하지 않으면서 +5.5%p를 챙긴다.
**구멍이 실제로 뚫린다.**

### 방어 후보 비교

**(a)/(b) 무작위 미끼도 거울 쌍으로 보내고, 빈도를 조절(`-pairfreq`) — 효과 없음.**

| 쌍 빈도 | SmartWallhack 이득 |
| --- | --- |
| 0% | +6.7%p |
| 25% | +6.3%p |
| 50% | +6.2%p |
| 75% | +6.9%p |
| 100% | +6.4%p |

(선공개 20ms·지연 20ms, 라운드 8,000개씩; C 표)

빈도를 0→100%까지 올려도 이득이 **전혀 줄지 않는다.** 이유: SmartWallhack은 "이 쌍이 진짜인지
미끼인지" 구별할 필요가 없다. 진짜 적 자신의 거울 미끼는 방향을 숨기려면 반드시 선공개 구간에
동반되므로, "쌍이 뜨면 곧 뭔가 보인다"는 타이밍 상관관계는 무작위 미끼를 아무리 쌍으로 위장해도
사라지지 않는다. 개수 기반 방어는 **방향** 누출은 막지만 **타이밍** 누출은 못 막는다 — SmartWallhack이
애초에 노리는 게 타이밍이라 이 방어는 표적을 빗나간다.

**(c) 선공개·지연 조합별 잔여 이득.**

| 선공개(ms) | 지연(ms) | 선공개−지연(ms) | 정직 승률 | SmartWallhack 이득 |
| --- | --- | --- | --- | --- |
| 20 | 20 | 0 | 31.0% | +6.4%p |
| 50 | 20 | 30 | 31.0% | +7.5%p |
| 100 | 20 | 80 | 31.0% | +6.8%p |
| 20 | 50 | −30 | 32.6% | +5.6%p |
| 50 | 50 | 0 | 13.3% | +4.6%p |
| 100 | 100 | 0 | 1.9% | +0.8%p |
| 200 | 20 | 180 | 31.0% | +7.7%p |

(쌍 빈도 100%, 라운드 8,000개씩; D 표)

"잔여 이득이 선공개−지연 크기로 제한된다"는 이 데이터에서 깔끔하게 맞지 않았다 — (선공개−지연)이
똑같이 0ms인 세 줄(20/20, 50/50, 100/100)의 이득이 +6.4%p, +4.6%p, +0.8%p로 다르다. 원인: 벽 뒤
신호와 실제로 보이는 신호가 **같은 지연선(같은 Delay)** 을 타기 때문에, 클라이언트가 느끼는 두 신호의
시간 차는 `(선공개 − 지연) + 지연 = 선공개` 그대로 남는다 — 지연이 양쪽에 똑같이 걸려서 상쇄된다.
즉 SmartWallhack의 타이밍 이득은 지연이 아니라 **선공개 자체**에 비례한다(지연=20 고정 줄들:
선공개 20/50/100ms → +6.4/+7.5/+6.8%p로 선공개 크기를 대략 따라간다). 50/50과 100/100에서 이득이
작아지는 건 지연이 커지며 정직 승률 자체가 13.3%, 1.9%로 짓눌리기 때문으로 보인다.

직접 확인: 선공개를 0ms로 내리면(지연 20ms 그대로, A 표와 같은 방식)

| 홀더 전략 | 미끼 켬 승률 | 이득 |
| --- | --- | --- |
| 정직 | 49.9% ± 1.1%p | 0 |
| SmartWallhack | 49.9% ± 1.1%p | **+0.0%p ± 1.5%p** |

**선공개를 0으로 하면 SmartWallhack의 이득도 정확히 0으로 접힌다.** 하지만 실험 1이 이미 보여줬듯,
선공개를 0으로 하면 정직한 사람도 팝인 때문에 공정성이 −17.3%p 깨진다(지연 20ms 기준).
**SmartWallhack의 타이밍 누출은 미끼로는 못 지운다. 선공개 구간을 없애야만 지워지는데, 그러면 게이트가
원래 풀려던 문제(팝인)가 그대로 돌아온다.** 이게 이 구조의 근본적인 한계다.

**(d) 행동 증거(반응 지연) — 측정했지만 못 쓴다.**

SmartWallhack은 쌍 신호 직후 에임을 전혀 움직이지 않는다(설계가 그렇게 만들었다). 대신 실제로 적이
보인 뒤 에임이 정렬되기까지 걸리는 시간(반응 지연)이 비정상으로 짧다는 점을 새 증거 후보
(`Result.FastR`, `duel.FastReactThr`=50ms 미만이면 "비정상")로 측정했다. 문제는 **정직한 사람도 이
값이 이미 높다**: 홀더가 할 일 없을 때 지키는 각도(`Holds`)에 정확히 두 출구 각도가 포함돼 있어서,
운 좋게 그 각도를 지키고 있다가 적이 나오면 정직한 사람도 "즉시 정렬"처럼 보인다. 실측 정직 비율
0.373(2배 하면 p₀ = 0.747) — SmartWallhack과 구별이 안 될 만큼 정직한 쪽 기저율이 이미 크다.
계정 판정(E 표)을 돌려보면 전략 6개 전부 밴 비율 0%, 최대 log₁₀E가 −1.9~−2.1 사이에 몰려 있어
**전혀 분리가 안 된다.** 이 신호로는 못 잡는다는 결론이다(원인은 `Holds` 각도 자체가 실제 출구
각도와 겹치게 설계된 것 — 바꾸면 p₀가 낮아질 수도 있지만, 이번 작업 범위에서는 검증하지 않았다).

### 최종 채택안

- **채택**: 무작위 미끼를 거울 쌍으로 보내는 기능(`Config.DecoyPairFreq`, `-pairfreq`, 기본값 1.0
  권장). SmartWallhack의 타이밍 누출은 못 막지만 비용이 0이고(정직한 승률·공정성에 측정 가능한 영향
  없음 — C 표), 더 단순하게 "개수만 보고 믿는" 다른 휴리스틱은 막아준다. 공짜 방어라서 뺄 이유가 없다.
- **유지**: 기존 B 표의 증거 규칙(무작위 미끼 반응, `DecoyR`). 신호를 부분적으로라도 **믿는** 월핵
  (신뢰 5~100%)은 전부 그대로 잡는다.
- **기각**: 반응 지연 기반 새 증거 규칙(d). 정직한 기저율(p₀ = 0.747)이 너무 높아 α=10⁻⁹에서
  쓸모가 없다.
- **미해결**: SmartWallhack류(개수를 안 믿고 신호를 방향이 아니라 타이밍으로만 쓰는 치트)는 이번
  방어로 못 잡는다. 3단계(사람이 직접 플레이) 이후, 4~5단계의 하드웨어 수준 반응시간 검증(픽셀
  에임봇 탐침·입력 서명)이 유일한 답일 가능성이 크다.

### 남은 한계 (숫자로)

| 항목 | 크기 |
| --- | --- |
| SmartWallhack 이득 상한 (선공개 20ms=지연 20ms, 쌍 빈도 100% 방어 적용 후) | **+6.4%p ± 0.9%p** (B 표 방식 증거로는 0% 밴) |
| 이 이득을 완전히 지우는 유일한 방법 | 선공개 → 0ms (정직한 공정성 −17.3%p 대가) |
| 새 행동 증거 규칙의 정직 기저율 | p₀ = 0.747 (사실상 못 씀) |

합격 기준(모든 치트 이득 상한 ≤ +1%p, 정직 계정 밴 0, 최대 log₁₀E ≪ 9)은 **기존 신뢰 기반 월핵
전부에 대해서는 충족한다**(신뢰 100%: 상한 −7.0%p, 50%: −4.8%p, 20%: −1.6%p, 5%: +0.4%p, 정직 밴
0%·최대 log₁₀E −1.7). **SmartWallhack에 대해서는 충족하지 못한다**(이득 상한 +6.4%p~+7.7%p, 선공개를
0으로 접지 않는 한). 이 실패는 숨기지 않고 위 표로 크기를 남긴다.
